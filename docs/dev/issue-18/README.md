# 全局快捷键截图

状态：开发实现已接入，原生成功路径仍需试用验证。需求：[Gupi #18](https://github.com/suxiaoshao/gupi/issues/18)。架构沿用[能力架构](../capability-architecture/README.md)与 [GPUI Kit Coding Guides](https://gpui-kit.com/docs/coding-guides/)。

## 用户结果

快捷任务增加“截图”来源，沿用任务的模板、模型和思考档位。按快捷键后冻结鼠标所在显示器的画面；左键拖拽并松开，裁剪所选区域后自动准备模板并发送。Escape、右键或离开选区窗口取消，不创建会话、不发送消息、不读取备用输入。

首版限定单个显示器内的矩形区域，主副屏都可作为目标，不做跨屏拼接。保留现有快捷键设置，不设置默认系统按键；不增加标注、OCR、录屏、截图历史或独立编辑器。

| 来源 | 采集规则 | 后续行为 |
| --- | --- | --- |
| Selection | 选中文本 | 有输入自动准备并发送；无输入保留模板草稿 |
| Clipboard | 剪贴板文字、图片或文件引用 | 有输入自动准备并发送；无输入保留模板草稿 |
| SelectionOrClipboard | 选中文字为空时读剪贴板 | 有输入自动准备并发送；无输入保留模板草稿 |
| Screenshot | 冻结画面后选择区域 | 成功自动准备并发送；取消直接结束 |

图片本身满足 `has_input`，不要求额外文字或截图专用确认。Pi 接受后才清空对应提交；发送失败保留图片和模板关联，等待期间的新草稿不被清掉。

## 捕获时序与所有权

隐藏遮挡内容的 Gupi 临时浮窗 → 捕获目标显示器原始画面 → 显示冻结帧与选区 → 裁剪同一帧 → 准备模板并自动发送。

- 捕获发生在选区窗口出现前，窗口覆盖的是保存的图像，不是实时桌面上的透明遮罩。完成后不再次截屏，也不延时取另一帧。
- 冻结时刻是浮窗隐藏后成功取得画面的时刻，不承诺等于热键事件的精确时刻。捕获和 PNG 编码在后台执行。
- 原始 RGBA 像素供裁剪，预览转换为 GPUI 所需的 BGRA。遮罩和边界不写入原图。完成、失败和取消释放帧、预览和窗口；截图包不写剪贴板或用户桌面。
- 捕获时保存显示器身份与逻辑边界，以图像实际尺寸和选区视口比例映射物理像素；反向拖拽归一化，越界钳制，零面积取消。创建选区与提交时检查显示器身份和边界是否变化。
- 全局只允许一个捕获请求。代次标识阻止取消后的后台结果、旧窗口事件和旧编码结果投递到下一次请求。退出由应用显式取消；取消后台任务不会承诺强行中断已经开始的系统同步捕获，但迟到结果不会打开窗口或发送。
- 原生隐藏、显示和前台恢复放在 App 借用之外。取消恢复此前的临时窗或前台应用；真实窗口合成时序仍需原生试用核对。

## 包与接口

| 所有者 | 职责 |
| --- | --- |
| `gupi-screen-capture` | 捕获请求、冻结帧、GPUI 选区、坐标裁剪、PNG 输出和取消 |
| 根应用 `src/app/shortcuts.rs` | 全局快捷键、四种输入来源、临时窗口协调、模板准备与自动发送 |
| `gupi-settings` 与设置编辑器 | 来源序列化、选择及本地化 |
| `gupi-conversation` | 附件文件所有权、准备状态和发送确认 |
| `gupi-conversation-ui` | 复用现有消息图片和失败草稿预览 |

截图包不依赖设置、会话或 Pi；平台依赖仅用于 macOS/Windows。`start` 返回异步任务，结果为 PNG、取消或类型化错误；`cancel` 由宿主在放弃任务和退出时调用，`is_active` 用于阻止重复入口。完整帧不跨会话边界传递。

包内 `capture.rs` 管理捕获、编码和请求；`overlay.rs` 管理选区界面；`selection.rs` 管理逻辑区域与像素坐标映射。平台差异目前收在捕获边界的条件编译中，不创建空平台模块。

应用通过 `Attachment::from_image` 建立已有的文件附件，再交给准备与发送流程。所有输入来源统一在模板读取成功后创建会话；准备失败不提前保留截图，用户重新触发截图。取消发生在模板读取和新会话创建前。没有配置 Pi 命令时仍显示现有启动入口，不绕过快捷任务的执行前提。

## 平台与依赖

当前使用 `xcap = "0.9.8"`（常规 Cargo 版本约束，非精确等号锁定）。本轮查询 crates.io 的最新发布版也是 0.9.8，许可证为 Apache-2.0；Jaco 历史版本仅作参考，不构成不能升级的约束。共享 GPUI Git revision 未变。

- macOS：`xcap` 通过 Core Graphics 抓取整屏；捕获前检查屏幕录制权限；未授权时调用 `CGRequestScreenCaptureAccess`，由 macOS 展示首次授权提示并记住用户选择。仍未授权时结束本次截图，不恢复前台应用或主动显示临时窗口，避免遮挡仍在显示的系统授权提示。权限说明通过系统通知投递，不依赖临时窗口是否可见；通知展示受系统通知权限与专注模式控制。用户在系统设置中允许 Gupi 后重试，按系统要求重启应用。已有权限时直接截图，普通捕获错误使用独立提示。当前路径不使用交互式 `screencapture -i`，不提高产品声明的系统下限。最低系统版本、Retina 和真实浮窗隐藏时序仍需相应环境验证。
- Windows：`xcap` 原生整屏捕获后进入相同 GPUI 选区，维持 MSI 身份；按原生显示器标识匹配目标，不凭相同分辨率猜测。不依赖 Snipping Tool 回调或剪贴板轮询。Windows 原生运行尚未验证。
- Linux：不增加全局快捷键后端，设置不展示截图来源选项，截图能力入口返回 Unsupported。

## 验证与试用

自动检查覆盖反向拖拽、边界与实际像素比例、PNG 裁剪后的 RGBA 像素。已有快捷任务测试继续验证准备和重复触发；设置本地化保持九种语言键一致。

本轮检查通过：`cargo fmt --all -- --check`、根应用构建，以及受影响包的 Clippy（所有 target，拒绝警告）。分次回归通过根应用 45 项、会话 32 项、设置 19 项、截图 2 项测试。收尾修改后重新通过根应用与截图包的 Clippy、根应用构建和截图测试。

原生试用入口：

```sh
cargo run -p gupi-screen-capture --example capture --locked
```

该窗口调用正式截图包，以持续更新的时钟观察冻结效果，不创建会话、不读取用户配置、不向模型发送图片。选取时钟区域，等待几秒后松开；结果应保持选区背景中的时间，与恢复后继续运行的时钟不同。再检查 Escape/右键取消、重复触发、主副屏及缩放、浮窗排除与恢复。示例界面为开发诊断用途。

此前原生证据：macOS 试用窗口正常启动，点击截图返回缺少屏幕录制权限。后续用户试用发现权限请求后的临时窗口会遮挡系统提示；修复权限失败路径不再激活窗口后，用户确认可以。尚未记录真实冻结选区、显示器映射与裁剪成功路径的验证；不能以编译或纯像素测试替代这些结论。没有 Windows/Linux 原生验证，也没有真实 Pi 截图发送验证。
