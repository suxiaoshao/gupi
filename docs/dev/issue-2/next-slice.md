# 下一步：三个独立工作的优先级讨论

状态：方向讨论。用户已确认共用设置页与项目入口方案，并要求编写开发文档；当前方案以[项目文件管理开发文档](../project-pi-files/README.md)为准。本页保留三项工作的边界与优先级比较，不授权实现。

## 工作边界

| 工作 | 讨论范围 | 当前基础与缺口 |
| --- | --- | --- |
| MCP | MCP 服务配置及相关管理流程 | 尚无专用界面；字段与协议见[MCP 盘点](mcp-configuration.md)。是否支持全局/项目是这项工作内部的设计问题，不代表完成了“项目配置”工作 |
| 项目配置 | 项目目录 `.pi/` 下的配置文件与资源；具体文件边界见下节 | 首批仅覆盖 settings.json 的部分字段；资源页仍仅管理全局 |
| 其他全局 Pi 配置 | MCP 之外尚未接入的全局配置能力 | 依据[覆盖统计](coverage.md)筛选普通设置、模型/供应商等能力；不能将整个工作预先定义成低频高级字段 |

三项分别确定范围、优先级和开发文档。共享作用域或文件能力只是实现依赖，不是合并工作边界的理由。

## 项目配置的文件边界（用户已明确）

项目配置指当前项目 `.pi/` 下的文件，不泛指所有与项目相关的设置功能。

| 文件或目录 | 内容 |
| --- | --- |
| `.pi/settings.json` | 项目设置、包声明（packages）和资源路径配置；已有部分字段编辑 |
| `.pi/SYSTEM.md` | 项目系统提示词替换 |
| `.pi/APPEND_SYSTEM.md` | 项目追加系统提示词 |
| `.pi/extensions/` | 项目扩展 |
| `.pi/skills/` | 项目 Skill |
| `.pi/prompts/` | 项目提示词模板 |
| `.pi/themes/` | 项目 Pi 主题资源 |

`.pi/mcp.json` 位于同一目录，但按三项工作划分归独立 MCP 工作。项目根目录或父目录中、位于 `.pi/` 外的 AGENTS/CLAUDE 指令文件不属于此项；全局 trust.json 的列表、撤销、拒绝等管理也不属于此项。项目信任仍是 Pi 加载相关文件的前提，沿用已有流程，不因此扩展出信任管理功能。

以上界定工作对象，不等于已决定为每种文件提供完整结构化编辑器。具体编辑方式及项目自身内容/有效合并结果的展示仍需设计。

## 共同推荐：先推进项目 `.pi/` 文件管理

协调者与设计师按三个独立工作重新讨论后，共同建议下一步选择项目 `.pi/` 文件管理。此为推荐，尚未获得用户实施选择。

理由：已有项目设置、作用域和信任基础，但资源页面目前仍只有全局操作。补齐项目文件管理能让现有 Pi 用户直接在 Gupi 内维护仓库配置，并复用已有文本编辑器。其他全局配置中的 Provider 认证和自定义模型同样有价值，不能整体当成低频字段；如果近期目标是让新用户无需 Pi 终端即可完成认证，则应改为全局认证优先。已有环境变量或 auth.json 凭据的用户不必等待 Gupi 的认证界面。

MCP 保持独立，不因为本轮刚完成其盘点而自动抢占下一批。项目工作内部按两个阶段推进，不在两阶段之间预先插入认证或 MCP；是否作为一个版本一起交付，尚未决定。

### 阶段一：项目文本资源

- 为 Skill 与提示词页面接入项目作用域，管理 `.pi/skills/`、`.pi/prompts/`、`.pi/SYSTEM.md` 和 `.pi/APPEND_SYSTEM.md`，与现有项目 settings 字段形成连贯入口。
- 编辑项目自有文件；全局来源只读显示并提供“在全局编辑”。首批不增加用项目过滤规则禁用全局资源的操作。
- 复用已有编辑器及其保存行为，不强行改成所有资源按页保存。
- 未信任项目可编辑文件，但明确 Pi 尚未加载；沿用已有显式信任流程。
- 先统一作用域、来源和信任展示方式。包页此阶段仍明确标注全局，不提供未完成的项目模式。

已核实 Pi 的 SYSTEM 和 APPEND 发现规则：可信项目的同名文件优先于全局文件；APPEND 是追加到系统提示词，不是把全局与项目两份 APPEND 文件拼接。Skill/提示词同名冲突的规则仍需核对，未经核实只标来源，不标“实际生效”或“被覆盖”。

### 阶段二：项目包管理

这是同一项目工作中的后续阶段。包声明属于 `.pi/settings.json`，因此在项目文件范围内。

当前 Gupi `package_action` 把 agent-dir 与 cwd 都设为全局 root，且没有 `--local`。项目包接入必须分离实际项目 cwd 和全局 agent-dir，核对各命令的 local 参数、安装位置、信任要求、全局/项目包身份去重与过滤 delta/autoload 规则。它不是把现有目录换成 `.pi/` 即可完成，故与纯文本编辑分阶段实现。

### 尚未收敛的范围和产品选择

- 用户是否选择项目优先，或因近期独立使用/认证目标改为其他全局配置优先。
- `.pi/extensions/`、`.pi/themes/` 及 settings 中的资源路径数组仍属于项目工作，具体 UI/编辑深度待设计；不能把阶段一或阶段二称为整个 `.pi/` 已全部完成。
- 项目文件管理两个阶段是内部里程碑还是分次交付，待用户选择交付范围时确定。
- 项目覆盖全局资源的启停/过滤不在阶段一推荐范围；是否随后加入保留为方案问题。

上述推荐未授权实现。下一步若选项目工作，应据此编写具体设计，核实资源来源/冲突和文件保存边界，再形成 Ready 方案。

## 已确认的页面方向

共用现有 Pi 设置页面，通过全局/项目作用域切换。对话与项目菜单提供入口，不新增常驻齿轮、对话内嵌设置或独立项目页面；作用域菜单增加“选择项目文件夹…”。详细流程、草稿保护和全局-only 页行为统一维护在[界面方案](../project-pi-files/interface.md)。

用户目前授权编写开发文档，没有要求开始实现。各阶段范围、待确定问题和验证计划见[开发方案](../project-pi-files/README.md)，此处不重复维护。

## 保留的技术事实与待调研项

- MCP 完整定义与项目局部覆盖有独立规则，不能套用 settings.json 的递归合并。
- 第三方扩展可能替代内置 MCP；识别方法待验证。
- Pi 对 mcp.json 的原地写入不使用 settings 的锁；基线比较只能检测已经发生的冲突，不能保证比较与替换之间没有竞争。具体写入契约在 MCP 工作中解决。
- `--no-session` 不能证明查询无扩展启动或 MCP 连接副作用。现有模型发现需要扩展模型，应根据实际启动行为核实，不能直接关闭扩展。这是待验证风险，不是已复现缺陷，也不意味着下一批必须做 MCP。

具体范围未选定前，不将 OAuth、项目完整服务、连接测试等标记为用户接受的纳入或排除项。
